The same reading, on AWS IoT Core

What changes if Mosquitto is replaced by a managed broker. Only the front door moves: the broker and its queue become AWS’s problem, and “acknowledge the broker” becomes “delete the SQS message”. Everything right of the worker — decode, dedup, storage, alerts, dashboard — is unchanged. Compare with BMS Live Architecture.html.

PostgreSQL before the delete

The raw message row commits first; only then is the SQS message deleted. An undeleted message becomes visible again when its visibility timeout lapses, so a failure anywhere before the commit simply means redelivery — the same promise the broker's manual acknowledgement used to make.

InfluxDB after the delete

Points are written last, and a failure there never costs a message. The row is already durable, so the backfill worker replays it later. Unchanged from the self-hosted design.

The queue stops being your problem

SQS holds messages for up to 14 days with no sizing exercise, against a broker session bounded in both messages and hours. Three production chores disappear with it: queue sizing, broker TLS renewal, and backing up the persistence file.

What this costs

Per-device certificates mean touching every device already in the field. The worker must be rewritten around SQS rather than MQTT manual-ack, re-earning the reliability tests. And a managed broker cannot run inside a plant — if a customer ever demands on-premise, Mosquitto is the only one of the two that can.
