    3 · Code structure

    Clean Architecture: dependencies point inward

    Business rules never reference MQTT, EF Core, InfluxDB or Next.js. Those are details that plug into the core, so a broker or database can be swapped without touching a rule.

    Bms.Api

    Composition root. REST controllers, SignalR hub, real-time bridge, offline and timeout sweeps. Wires everything together.

    Bms.Ingestion

    Separate host process: MQTT worker, InfluxDB backfill worker, liveness status publisher.

    Bms.Protocols

    MQTT transport and the JSON decoder — the gateway sends BMS parameter keys, so there is no per-vendor mapping.

    Bms.Alerting · Bms.Calculations · Bms.DeviceManagement

    Alert rule evaluation, derived values such as energy consumption, device online/offline lifecycle.

    Bms.Infrastructure

    EF Core + PostgreSQL repositories, InfluxDB store, email and Telegram senders, OTA firmware storage.

    Bms.Application

    Use cases (the ingestion pipeline, normalizer, backfill) and the interfaces every outer project implements.

    Bms.Domain

    Entities and rules: Device, Tenant, Site, RawDeviceMessage, Alert. No dependencies at all.

    5 · Reliability rules

    Why a temporary outage does not lose telemetry

    Persistent MQTT session

    Ingestion connects as bms-ingestion with MQTT 5, Clean Start off and a 24 h session expiry. While it is away, Mosquitto queues every QoS 1 message for it.

    Acknowledge only what is stored

    The broker is told "received" only after the PostgreSQL row is committed. If PostgreSQL is down, nothing is acknowledged and the message is retried or redelivered.

    Bad messages never block

    Malformed payloads, failed validation and unknown devices are recorded as Rejected and acknowledged, so one bad message cannot stop the queue.

    Duplicates stored once

    Identity comes from the device's own sequence number and timestamp. A redelivered copy matches; a reset or wrapped counter does not.

    InfluxDB backfill

    A reading that misses InfluxDB keeps TimeSeriesWrittenAt empty. The backfill worker rebuilds it from the raw payload and writes it later.

    No false offline alarms

    Ingestion publishes a retained online / degraded / offline status. The API pauses device-offline checks while ingestion is down or draining a backlog.

    FailureTelemetry sent during itLimit
    Ingestion stopped or crashedQueued in Mosquitto, delivered on restart (Docker restarts it)24 h session, max_queued_messages
    PostgreSQL downNot acknowledged, held in the broker, processed when it returnsBroker queue size; devices reconnecting need PostgreSQL to log in
    InfluxDB downStored in PostgreSQL, backfilled laterNone while PostgreSQL is up
    Mosquitto restarted cleanlyQueue saved and restoredDevices must buffer while it is down
    Mosquitto crash / power lossRestored from the last saveUp to 60 s of queued messages
    6 · Deployment

    Today on Docker Compose, target on AWS

    The AWS target keeps the same services. Only the broker runs on a virtual machine; the rest are containers and managed databases.

    EC2 · 1 VM

    Mosquitto broker

    Own VM so app restarts never stop data collection. EBS volume for mosquitto.db, NLB on 8883.

    ECS Fargate · 1 task

    Ingestion

    Exactly one copy, because it owns the bms-ingestion session. Deployed stop-then-start.

    ECS Fargate · 2+ tasks

    API

    Behind an ALB with WAF. Needs a per-task MQTT client id and one sweeper before scaling out.

    ECS Fargate · 2 tasks

    Dashboard

    Next.js behind CloudFront and the ALB.

    Amazon RDS

    PostgreSQL 17

    Multi-AZ in production, point-in-time backups, SSL required.

    Timestream for InfluxDB

    InfluxDB v2

    Managed, same API and Flux queries. Choose v2, not v3.

    Shared

    Secrets, certs, logs

    Secrets Manager, ACM, KMS, CloudWatch, S3 for firmware and backups, SSM for VM access.
