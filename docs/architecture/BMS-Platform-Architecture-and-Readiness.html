What the platform does

Field devices publish readings over MQTT. The platform decodes each vendor's payload into a common shape, stores the original bytes and the normalized reading, evaluates alert rules and derived values, and pushes live updates to a browser dashboard.

  • Multi-tenant. Every device, reading and alert belongs to a tenant and a site; access is scoped by JWT claims and enforced again at the broker by per-tenant MQTT ACLs.
  • Vendor-agnostic. Our own gateway reads each device in its native protocol and publishes JSON over MQTT keyed by BMS parameter keys, so BMS never handles vendor formats.
  • Never discards raw data. The exact bytes received are kept, so a vendor's malformed message can be debugged and replayed after a decoder fix.
  • Survives its own outages. Each dependency can fail independently without losing a reading. Section 5 states exactly what is guaranteed.

The journey of one reading

1Device publishes to iot/{tenant}/{site}/{device}/telemetry at QoS 1 over TLS.
2Mosquitto delivers it to the bms-ingestion persistent session.
3The worker decodes, validates and deduplicates it in memory.
4The raw bytes are committed to PostgreSQL.
5Only now is the broker acknowledged. Anything that failed before this point is redelivered.
6The normalized point is written to InfluxDB.
7Device status, calculations and alert rules run; critical alerts go to email and Telegram.
8A live event is published back to the broker; the API re-broadcasts it over SignalR to the dashboard.

Steps 4 and 5 in that order are the core design decision. Everything in section 5 follows from it.

Why ingestion is a separate process

Ingestion must keep draining the broker whether or not anyone is using the API, and it must be restartable and scalable on its own schedule. Splitting it costs one thing: real-time events generated there cannot reach the API's in-memory SignalR hub directly.

Rather than introduce Redis or another backplane for that one hop, the worker publishes events to an internal topic on the broker the platform already runs — bms/realtime/events — and the API subscribes and re-broadcasts them. The same hop carries the retained ingestion status topic and the worker's MQTT last will, which is how the dashboard distinguishes "ingestion is down" from "every device went quiet".

Trade-off accepted: that channel is best-effort — it is skipped while the broker is disconnected and its failures are logged and dropped. PostgreSQL and InfluxDB, not the event channel, are the source of truth. A missed event costs UI freshness, never data.

4 · What the system guarantees, and why

PostgreSQL commits before the acknowledgement

The worker uses manual acknowledgement. The raw row commits first; only then is the broker told the message is handled. A message that fails anywhere before that point is never acknowledged, so the broker redelivers it after a retry or a reconnect.

InfluxDB is written after the acknowledgement

A failed point write therefore never fails a message. The row stays marked unflushed and the backfill worker replays it — with exponential backoff while InfluxDB is unreachable, and immediately again while a backlog is draining.

Redelivery is safe

A duplicate key is built from what the device itself sent — sequence number and device timestamp — so a redelivered copy produces the same key while a genuinely new reading does not. A unique index on (DeviceId, DedupKey) settles any race the check loses.

A bad message cannot stop the queue

A failure that is about the message itself is recorded as Rejected with the reason and acknowledged, rather than blocking everything behind it. Only infrastructure failures are retried.

Downstream effects are isolated

An InfluxDB outage must not also stop device-status tracking or alert evaluation — arguably more important during an outage than the chart. Each effect catches its own failures. The same applies per notification channel.

Nothing is discarded

Rejected and duplicate messages are kept with their reason. The original bytes are always preserved, which is what makes replay after a decoder fix, and proving what a vendor actually sent, possible.

6 · Decisions taken, and the conditions to revisit them

Each of these was a deliberate choice to not add infrastructure. None is permanent; each has a stated trigger. The point of writing them down is so the next person does not re-litigate them from scratch, and does not adopt them out of habit either.

Not usedWhat it would solveWhy it is not needed hereAdopt it when
Kafka A durable, replayable log with many independent consumers, partitioned for horizontal scale. Devices speak MQTT only, so Kafka could not replace Mosquitto — it would be added behind it, as a second broker and an extra hop. The durable log already exists as the raw message table, and the backfill worker already replays from it. There is exactly one consumer today. A single-broker Kafka on one host also runs at replication factor 1, which is weaker than the PostgreSQL commit the system currently trusts. Two or more of: one ingestion process provably cannot keep up in normal operation; three or more jobs are scanning the raw table on their own schedules; reprocessing days of raw data across the fleet is too slow in PostgreSQL; the required buffer is hours rather than minutes; an external party needs a live feed. And someone owns operating it.
Redis or another backplane Pub/sub between the ingestion process and the API's SignalR hub. One internal MQTT topic on the broker already running does the same job with no new service, no new port and no new failure mode. The event volume or the delivery guarantees outgrow a best-effort channel — for example if a missed UI event ever becomes a correctness problem rather than a freshness one.
Kubernetes Multi-node orchestration for independently scaled services. Six containers on one host with restart policies and health checks. There is no fleet to orchestrate. Multiple nodes, independent scaling per service, or zero-downtime rolling deploys become a requirement.
Microservices Independent deployability and scaling boundaries. The boundaries that matter — transport, protocol, payload format, mapping, domain versus time-series storage — are already enforced in-process by Clean Architecture. Splitting them over the network would add latency and distributed failure modes for no benefit at this size. A specific boundary genuinely needs to scale or ship separately. Ingestion was split out for exactly that reason and is the precedent to follow.

7 · What we still need before production

The architecture is sound and the failure behaviour is tested. What follows is not redesign work — it is the operational gap between "it works on the stack" and "it runs unattended with real devices and real money on it". Items marked must should block go-live.

The cheaper moves to try before any of the above. In order: batch the InfluxDB writes instead of one point per message; enable MQTT 5 shared subscriptions and run two or three ingestion instances; time-partition the raw message table; then re-measure. Each is days of work rather than a new platform to operate, and together they move the ceiling a long way.
ItemWhy it mattersWhat done looks like
must Raw message retention There is no retention or cleanup worker in the codebase today. RawDeviceMessages stores the full payload of every message forever. At the target device count this fills the disk, and a full disk stops the acknowledgement path — which is the one thing that must never stop. An agreed retention window, a worker that enforces it, and the table time-partitioned so deletes are a partition drop rather than a mass delete.
must Size the broker queue against real numbers The current limits are 100,000 messages / 100 MiB. At 10,000 devices reporting once a minute that is roughly 10 minutes of outage cover; at once every 10 seconds it is roughly 60 seconds. Beyond the limit Mosquitto drops silently. The 24-hour session expiry is not the real bound — the queue is. The sizing formula in docs/mqtt/reliability.md applied to the real device count and interval, the limits set accordingly, and the volume sized for the bytes.
must Real secrets and real certificates .env.example ships change-me placeholders for the database, InfluxDB token and all MQTT accounts. The TLS listener needs a certificate that devices will actually trust. Generated credentials held in a secret store with a rotation plan, a real CA and server certificate on 8883, and anonymous access confirmed off.
must Decide the PostgreSQL coupling posture PostgreSQL is both the acknowledgement boundary and the broker's device-authentication backend. During a PostgreSQL outage, devices that try to reconnect are refused, so an outage does not only pause processing — it can push devices off the broker entirely. A conscious decision: cache authentication lookups, use a read replica for auth, or accept it and tell device vendors what buffering they must do. Any of the three is fine. Not knowing is not.

7 · What we still need before production · continued

ItemWhy it mattersWhat done looks like
must Backups and a restore drill Three stateful volumes — pgdata, influxdata, mosquitto-data. A backup that has never been restored is not a backup. Scheduled backups for both databases, off-host, plus one rehearsed restore with the time it took written down.
must Monitoring and alerting The counters already exist — processing latency, messages persisted / rejected / duplicate, transient failures, time-series write failures — but nothing watches them. Without that, an outage lasts until a user complains. Those metrics plus broker queue depth and the ingestion status topic on a dashboard, with alerts on queue depth rising, rejection rate and the worker going offline.
scale Shared subscriptions for more than one ingestion instance Ingestion runs under a single client id with a persistent session, so a second instance cannot be added — it would fight for the same session. This is a hard ceiling, and it is the first one you will hit. MQTT 5 shared subscriptions ($share/...) proven on the stack, so scaling out is a configuration change rather than a redesign under pressure.
scale Batch the InfluxDB writes One point write per message is the simplest thing that works and the first thing to become a bottleneck. Buffered writes with a size and time trigger, with the unflushed marking still correct so backfill keeps working.
scale Load test at the target device count Every number in this document about capacity is an estimate. One test replaces all of them with facts, and sizes items 2, 7 and 8 properly. A simulated run at the real device count and interval, with processing latency and queue depth recorded.
tidy One code comment contradicts the code MqttRealtimeNotifier documents the bridge as QoS 0, but it publishes through an adapter that hardcodes QoS 1. Harmless today; misleading to whoever reads it next. Either correct the comment or make the publish QoS a parameter, depending on which behaviour was intended.
