BMS Telemetry Flow

A meter reading crosses a broker, survives five checks, lands in two stores, and reaches a browser in under a second. The Calculations module adds a second, derived value along the same path — without touching the first.

2 processes MQTT via our gateway JSON payloads PostgreSQL + InfluxDB SignalR

One reading, end to end

Devices never talk to the API. Everything arrives through Bms.Ingestion, which owns the transports and the pipeline; Bms.Api serves the dashboard and holds the realtime hub.

After a reading is accepted, five things happen — separately

Each runs in isolation, so one failure can't take the others down. An InfluxDB outage must not also stop alerting, which matters more during an outage, not less.

  1. Write the reading to InfluxDB.
  2. Update the device's last-seen state.
  3. Push TelemetryUpdated to the dashboard.
  4. Run Calculation Rules and push any derived value.
  5. Evaluate Alert Rules, then email and Telegram for critical ones.

Inside the pipeline

Seven stages between a raw frame and a stored reading. Five can reject; one silently drops fields, which is a different thing and drawn differently.

The filter is the quiet one. A device may send more fields than the Device Type declares; anything not on the allow-list is dropped and the rest of the reading is kept. Parameters marked Derived are excluded here too — a device can never overwrite a calculated value.

Calculations: two paths, one definition

Energy Consumption is derived from a cumulative Totalizer. The live path keeps a running baseline; the history path recomputes from raw readings on request. Both apply the same rules, which is why they agree.

A totalizer is declared, not guessed. Eligibility comes from a parameter's Kind — Instantaneous, Counter, Digital or Derived — never its unit. An energy parameter in kWh that isn't marked Counter is rejected as a source, because kWh alone doesn't make a value cumulative.

Which devices a rule reaches

Scope says which devices a rule can apply to. How it applies decides whether it reaches them on its own or waits to be picked in the device form.

Realtime across two processes

The hub lives in the API, but readings arrive in ingestion. Events cross on the broker the platform already runs, rather than adding a second piece of infrastructure.
