PostgreSQL before the ack

The worker uses manual acknowledgement. The raw message row commits first; only then is the broker told the message is handled, so an unacknowledged message is simply redelivered.

InfluxDB after the ack

Points are written last, and a failure there never fails the message. The row is already durable, so the backfill worker replays it later.

The queue is the buffer

With a persistent session and a 24-hour expiry, a restart of the ingestion worker costs nothing but latency: Mosquitto holds the QoS 1 messages and delivers them on reconnect.

Live updates ride the broker

Ingestion and the API are separate processes, so the worker publishes events to bms/realtime/events rather than adding a Redis backplane. It is best-effort — skipped while the broker is disconnected, failures logged and dropped — so PostgreSQL and InfluxDB, not that channel, remain the source of truth.

Only the device can lose data

If the broker itself is unreachable, devices buffer or drop. That is the one hop where the platform cannot promise delivery.
